## Goal

A workflow moves the pinned proofline commit by itself: started by hand with a commit id, or on a weekly schedule that follows the newest proofline tag, it opens or updates one pull request that changes `sync/pin.json` and `sync/lock.json`, lists the added, removed and changed documents, and stays a labelled draft when the build is red.

## Context

Launch scope decision, in the product owner's words:

Yayından önce proofline sürümü elle güncellenir.

PRD section "Launch scope decision (2026-11-20)", L-1: until this workflow exists the owner updates the pin by hand with the lock script of TASK-007. This task is no dependency of any launch task.

- ADRs: `/docs/adr/0003-document-sync-pin-lock-and-sync-workflow.md` points 1, 2 and 8 (the workflow, the branch `sync/proofline`, tag-follow, red pull request, permissions), `/docs/adr/0008-ci-checks-budgets-and-workflow-permissions.md` points 1 and 3 (workflow rules, one required check).
- Today: `scripts/sync.mjs` (TASK-007) has the `lock` command that writes `sync/lock.json` from a commit; `sync/pin.json` is `{commit, tag}`; `.github/workflows/ci.yml` triggers on `pull_request` and `push` to `main`; `scripts/check-workflows.mjs` (TASK-033) rejects secrets other than `GITHUB_TOKEN`, a missing or `write-all` permissions block.
- Expected scope: `.github/workflows/sync.yml` (new), `scripts/sync.mjs`, `scripts/lib/sync-pr.mjs` (new: target choice, PR body, issue dedupe), `tests/sync-workflow.test.mjs` (new), `tests/fixtures/sync-pr/` (new: compare-API answers, two lock files). 5 paths.
- Assumption: a manual start with a commit id writes `"tag": null` unless a tag points at that commit, which the script reads from the same tag list.
- Assumption: only a compare status `ahead` moves the pin on tag-follow; `identical`, `behind` and `diverged` do not (ADR 0003 leaves the meaning of each value unverified, TASK-036 reads it from the real API).

## Acceptance criteria

- AC-1: `sync.yml` is parsed -> its only triggers are `schedule` (one weekly cron expression) and `workflow_dispatch` with an optional input `commit`; there is no `pull_request`, `pull_request_target` or `push` trigger.
  Covers: FR-11
- AC-2: `sync.yml` is parsed -> its top-level `permissions` are exactly `contents: write`, `pull-requests: write` and `issues: write`, the only secret it uses is `secrets.GITHUB_TOKEN`, and `node scripts/check-workflows.mjs` exits 0 on the real workflows directory.
  Covers: NFR-8
- AC-3: The sync script is run with a 40-character `commit` input and a fixture of the proofline repository -> the branch `sync/proofline` differs from `main` in exactly 2 files, `sync/pin.json` (the new commit) and `sync/lock.json` (regenerated by the lock command), and no document is copied into the repository.
  PRD ids: AC-15.
  Covers: FR-11
- AC-4: The sync script compares two fixture locks -> the pull request body lists every added, removed and changed document by path under three headings, and a lock pair with no difference makes the script report "nothing to sync" and open no pull request.
  PRD ids: AC-15.
  Covers: FR-11
- AC-5: A scheduled run finds in the fixture tag list the tags `v0.0.171`, `v0.0.173` and `v0.0.174` where the compare answers `identical` for `v0.0.173`, `ahead` for `v0.0.174` and `behind` for `v0.0.171`, and no sync pull request is open -> the script targets `v0.0.174` and opens a pull request that moves the pin to its commit with `"tag": "v0.0.174"`.
  PRD ids: AC-19.
  Covers: FR-11
- AC-6: A scheduled run finds no tag whose compare status is `ahead`, or a pull request for the same target is already open -> the script opens no pull request and changes no branch.
  PRD ids: AC-19.
  Covers: FR-11
- AC-7: A sync pull request is open and a newer target is due (a manual start with another commit, or a newer tag) -> the script force-pushes the same branch `sync/proofline` and edits the same pull request (title and body), and the number of open pull requests from that branch stays 1; a manual start overrides a tag-follow target.
  Covers: FR-11
- AC-8: The job builds the target (`npm ci` and `npm run build`) before it opens or updates the pull request, and the build exits non-zero -> the pull request is opened or kept as a draft with the label `sync-red`, its body holds the last lines of the build log and a ready text for an issue in the proofline repository (the failing path or sentence, the pinned commit and the target), and nothing is merged.
  Covers: FR-11
- AC-9: The workflow is read -> it starts no other workflow (no `workflow_dispatch` call of `ci`, no `gh workflow run`), and `.github/workflows/ci.yml` still triggers on `pull_request` without a branch filter, so the check starts on the sync branch.
  PRD ids: AC-16.
  Covers: FR-13
- AC-10: The tag list and the compare answer are read through the GitHub API -> every request carries the job's `GITHUB_TOKEN` as bearer and none carries another credential.
  Covers: NFR-8
- AC-11: Failure criterion (anti-goal): the task is not done, even when the fixture tests are green, if two sync pull requests can exist at once, if a document or a generated page is committed, if the workflow uses a personal token or a secret other than `GITHUB_TOKEN`, if it pushes to `main`, or if a red build is merged; the tests fail in each of these cases.

## Out of scope

- Turning on the repository setting "Allow GitHub Actions to create and approve pull requests" and the first real sync pull request with its approval-required run (TASK-036); local tests parse the workflow and run the scripts on fixtures.
- The branch ruleset (TASK-034). The lock script itself (TASK-007).
- Promoting a red sync pull request to ready after a later green run: the PRD does not specify it, the maintainer does it by hand.
- Filing the ready issue text in the proofline repository (by hand; `GITHUB_TOKEN` cannot open an issue in another repository).

## Constraints

- Expected test exception: the behaviour of real GitHub (approval-required runs for `GITHUB_TOKEN` pull requests, compare status values, label and draft state) cannot be reproduced locally; it is observed in TASK-036. Tested instead: the workflow file and the scripts on fixtures with a fake API.
- ADR 0003 point 8: one long-lived branch `sync/proofline`, at most one open pull request, updated in place by force-push; the credential is the workflow's `GITHUB_TOKEN`; the check is `ci / verify` of ADR 0008.
- NFR-8: permissions are the least the job needs; no other secret exists.
- A workflow with write permissions and pull-request creation: CRITICAL is considered and taken (see Suggested class).

## Risks

- ADR 0003 (confidence medium on point 8): the approval-required state of a `GITHUB_TOKEN` pull request is inferred; TASK-036 settles it, and a different behaviour would change the review step, not the files this task writes.
- A force-push replaces the branch history of an open pull request; reviewers lose inline comments on an older target.
- Scheduled workflows of a public repository stop after 60 days without activity (ADR 0007); this task cannot prevent it.
- An upstream rewording of a guarded sentence keeps every sync pull request red by design (ADR 0003 Consequences).
