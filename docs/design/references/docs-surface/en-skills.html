Skill catalogue

Taken from proofline v0.0.173

proofline ships 28 skills. A skill is one method with one rule, run by a role of the workflow. Each page states the rule first, then the hard rules and the flow.

api-design
Designs or changes API contracts.
concurrency-proof
Concurrency review of a change (working tree, branch, pull request or proofline run) that reports only proven problems.
contract-proof
Proves backward and forward compatibility of changed API, event and data contracts (OpenAPI/Swagger, AsyncAPI, JSON Schema, GraphQL SDL, protobuf, whichever the repository has).
data-design
Designs the data side of a change for the project's actual database - data model, Mermaid ERD, invariants, and a migration plan with expand/contract steps, batched idempotent resumable backfill, reversibility and rollback per step, lock risk per statement, and a data-loss assessment.
debug-proof
Debugs a failure with proof instead of guesses.
design-sync
Checks durable design documents against the code and reports drift as `doc:line -> missing code fact` - every table in DATA_MODEL.md exists in the schema or migrations, every path in ARCHITECTURE.md exists, every endpoint in API.md (or an OpenAPI file) exists in the routes, every token and component named in DESIGN.md exists where the doc says.
docs-writer
Writes and maintains project documentation that matches the code and follows a writing profile.
evidence-map
Bounded codebase investigation that returns compact, verified evidence.
explain-html
Explains a topic, a task, a review or a completion report as one self-contained HTML page with inline SVG diagrams, inline CSS and JS, a light and a dark theme, and no network request.
exploit-proof
Defensive security review of a change in the user's own repository (working tree, branch or pull request) before merge.
intent-grill
Interviews the user about a vague or high-stakes request before a task is written.
llm-wiki
Keeps a persistent, Git-backed Markdown wiki under docs/wiki that grows with the project instead of rediscovering facts on every question.
performance-proof
Proves or refutes a performance regression by measurement, never by reading code.
plan-contract
Writes an executable, scoped PLAN.md for one task and validates it mechanically.
product-assess
Tests the assumptions behind a product plan with the user in the main session - lists the assumptions with risk type, importance and evidence level and marks the riskiest, designs probes whose success and failure thresholds are locked before they run, runs a premortem, has an independent strategy reviewer attack the most-trusted assumptions, records one decision (build, clarify or stop) as a short ADR, and after the build records the outcome against a measured baseline and target.
product-discovery
Discovers a product problem with the user in the main session before a PRD exists - frames the problem and its limits, researches the market from a written search plan and sources, runs and synthesises user interviews, profiles competitors beyond a feature table, and lists and ranks opportunities with the evidence behind each - into docs/product/<slug>/ (FRAME, RESEARCH, INTERVIEWS, COMPETITORS, OPPORTUNITIES).
product-spec
Writes a product requirements document (PRD) with the user in the main session - problem and whose problem it is, goals, non-goals, user stories with acceptance criteria, FR-n and NFR-n requirements, success metrics that say how they are measured, assumptions, a completeness list (error states, permissions, personal data, security, performance, accessibility, languages, analytics, rollout, dependencies), blocking and non-blocking open questions - to docs/product/<slug>/PRD.md.
proof-review
Reviews a code change (uncommitted work, a branch, or a PR) and reports only what it can prove.
proofline
The user-facing /proofline entry point.
proofline-lead
The proofline lead's lifecycle method for the main session (AGENT_ROLE unset = lead).
qa-plan
Independent QA in two phases.
system-design
Designs the smallest valid architecture for a task, or reverse-engineers docs/design/ARCHITECTURE.md from an existing codebase.
task-author
Turns a one-sentence request or an external issue (GitHub, Jira, Linear, markdown) into the canonical TASK.md - goal, context, numbered observable acceptance criteria, explicit out of scope, constraints, risks, suggested class with the indicator that placed it - and renders it into a per-target template (project templates in .agents/templates/tasks/ win over the bundled ones).
tdd-proof
Implements a change test-first with recorded proof.
test-trust
Audits how far a test suite can be trusted, using runnable evidence instead of opinion.
ui-design
Designs UI work.
verify-proof
Mechanical proof that a frozen plan was implemented - every acceptance criterion has a passing test or, when every mapped PLAN scope path has a tdd_exemption, recorded passing command evidence; changed paths stay inside scope; build, test and lint commands pass.
visual-proof
Visual proof of a UI change with the browser tooling the project or machine already has (a project browser-test dependency or an installed headless Chromium-family browser; a runtime browser tool only as an adapter).
